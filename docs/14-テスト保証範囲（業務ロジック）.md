# テスト保証範囲（業務ロジック）

最終更新日: 2026-03-01

## 目的

本ドキュメントは、現在の自動テストが業務ロジックとして何を担保しているかを整理したものです。  
実装詳細ではなく、利用者・管理者の業務上の期待値に対して「何が壊れないことを確認しているか」を示します。

## 対象テスト

- `tests/test_auth_routes.py`
- `tests/test_attendance_routes.py`
- `tests/test_permissions_and_csrf.py`
- `tests/test_admin_shift_edit_and_export.py`
- `tests/test_admin_users_routes.py`
- `tests/test_admin_audit_routes.py`

合計 61 テスト（HTTP統合テスト中心）

## 担保している業務ロジック

## 1. 認証・セッション

- 正しい認証情報でログインできる
- ログイン成功時に最終ログイン時刻が更新される
- ログイン成功時に監査ログ（`login`）が残る
- 認証失敗時はログイン画面へ戻り、成功扱いの監査ログは増えない
- CSRF不正のログアウトは拒否される（400）
- 正常ログアウト後は再度保護画面へ直接アクセスできない
- ログアウト時に監査ログ（`logout`）が残る

業務上の意味:
- なりすまし・誤認証を防ぎ、認証イベントの追跡可能性を維持する

## 2. 勤怠打刻（出勤・退勤・休憩）

- 出勤操作で「開いているシフト」が1件作成される
- 出勤中に再度出勤はできない（重複出勤防止）
- 出勤していない状態で退勤はできない
- 休憩中に退勤した場合、休憩は自動で終了して退勤できる
- 出勤していない状態で休憩開始はできない
- 休憩中に再度休憩開始はできない（重複休憩防止）
- 休憩中でない状態で休憩終了はできない
- 正常な休憩終了時に休憩終了時刻が記録される
- 打刻関連操作で監査ログ（`clock_in`, `clock_out`, `break_end`）が残る

業務上の意味:
- 「1ユーザー1つの稼働状態」を保ち、打刻の状態遷移を破綻させない

## 3. 権限・アクセス制御

- 未ログイン利用者は管理画面へ直接アクセスできない
- 一般ユーザーは管理画面へアクセスできない（403）
- 一般ユーザーは管理者向けシフト詳細APIへアクセスできない（403）
- CSRFトークンなしの更新系操作は拒否される（400）

業務上の意味:
- 管理機能の誤操作・不正操作を防ぎ、権限境界を維持する

## 4. 管理者によるシフト編集

- 管理者は対象ユーザーのシフトを作成できる
- シフト作成時に「退勤 < 出勤」の不整合は受け付けない
- シフト更新時に時刻が更新され、監査ログへ変更前後値が残る
- 管理者は休憩の追加・更新・削除・一括リセットを実行できる
- 休憩操作ごとに対応する監査ログが残る
- シフト詳細APIが編集画面に必要なJSON（時刻・集計値）を返す

業務上の意味:
- 訂正業務を安全に実施でき、あとから監査で変更履歴を追跡できる

## 5. CSVエクスポート

- 管理者は期間指定でCSVを取得できる
- CSVはUTF-8 BOM付きで出力される
- エクスポート時に監査ログ（`admin_export`）が残る
- 日付形式が不正なリクエストは拒否される（400）
- 最大期間を超えるリクエストは拒否される（400）
- `username` フィルタ指定時、対象ユーザーのみ出力される

業務上の意味:
- 月次集計・外部提出向けのデータ抽出が要件どおり実行できる

## 6. ユーザー管理（管理者機能）

- 未ログイン利用者は `/admin/users` を利用できない
- 一般ユーザーは `/admin/users` の GET/POST ともに拒否される（403）
- 管理者のPOST操作でCSRF不正は拒否される（400）
- ユーザー作成（`action=create`）の正常系が成立する
- 作成時の必須不足（ユーザーID/パスワード）で作成されない
- 作成時のユーザーID重複・メール重複で作成されない
- 作成時のDBコミット失敗でロールバックされる
- ユーザー更新（`action=update`）の正常系が成立する
- 更新時にパスワード空入力なら既存パスワードを維持する
- 更新時に新パスワード入力ならハッシュが更新される
- 更新時の他ユーザーとのメール重複は拒否される
- 更新対象が存在しない場合は404になる
- 更新時のDBコミット失敗でロールバックされる
- ユーザー削除（`action=delete`）の正常系が成立する
- 自己削除は拒否される
- 削除対象が存在しない場合は404になる
- ユーザー削除時に対象ユーザーの既存監査ログ `user_id` はNULL化される
- 未知の `action` は副作用なく一覧再表示になる
- 作成/更新/削除の各操作で監査ログ（`admin_user_create`, `admin_user_update`, `admin_user_delete`）が適切に残る

業務上の意味:
- アカウント管理運用の整合性（重複防止・誤削除防止・監査追跡）を維持できる

## 7. 監査ログ閲覧・監査CSV

- 未ログイン利用者は `/admin/audit` と `/admin/audit/export` を利用できない
- 一般ユーザーは監査画面・監査CSVを利用できない（403）
- `action` フィルタと `username` フィルタが画面表示・CSV出力に反映される
- 画面側 `limit` は `default=200`, `min=1`, `max=500` の境界で補正される
- CSV側 `limit` は `default=1000`, `min=1`, `max=5000` の境界で補正される
- 不正JSONの `metadata_json` が混在しても、画面表示・CSV出力が継続できる（raw fallback）
- 監査CSVはUTF-8 BOM付きで出力される
- 監査CSV実行時に `admin_audit_export` の監査ログが残る
- 監査CSV内には「実行中に新規追加された `admin_audit_export` ログ」は含まれない

業務上の意味:
- 監査証跡の検索性・可搬性を保ちながら、壊れたデータ混在時でも運用停止を防げる

## 現時点で未担保（このテストセットの範囲外）

- テンプレート内JavaScript挙動のE2E検証（モーダルUI操作など）
- パフォーマンス要件、同時更新競合の高負荷シナリオ
- 監査署名（HMAC）の再計算一致まで含む厳密検証
